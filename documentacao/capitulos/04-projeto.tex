\section{Arquitetura do Sistema}

O \sistema{} adota uma arquitetura cliente-servidor com três partes: a interface web, executada no navegador; a API, que concentra as regras de negócio; e o banco de dados PostgreSQL. Toda leitura e escrita de dados passa pela API, e a comunicação com os marketplaces também parte dela, de modo que a interface web não depende das particularidades de nenhuma plataforma externa.

A API é uma única aplicação, organizada internamente em camadas e implantada como um só processo. Uma arquitetura de microsserviços, com um serviço para cada módulo, foi descartada: o sistema atende a uma única loja, a equipe é pequena e a divisão acrescentaria comunicação em rede e implantação independente sem benefício para esse volume de uso. A separação em camadas preserva a organização do código sem esse custo.

Duas decisões sustentam a integração entre canais. A primeira é o modelo canônico: cada produto é cadastrado uma única vez no banco e depois mapeado para as categorias e os atributos de cada marketplace. Os dados comuns ficam em colunas tipadas, e os campos específicos de cada canal, em colunas JSONB. A segunda é a interface \texttt{ConectorMarketplace}, com uma implementação por canal, que isola as diferenças entre as APIs das plataformas. Assim, os serviços de negócio operam sempre sobre o modelo canônico, e incluir um novo canal exige apenas uma nova implementação da interface.

\section{Projeto dos Componentes}

Os componentes da \autoref{fig:componentes} organizam o sistema pelos módulos do domínio. Na API, cada módulo segue as camadas descritas na \autoref{sec:estrutura} (controlador, serviço e acesso a dados), e a interface web mantém telas e serviços próprios para consumi-los. As responsabilidades de cada componente são:

\begin{description}
  \item[Usuário:] mantém as credenciais, verifica o acesso ao sistema e identifica o vendedor responsável pelos dados, informação fornecida ao componente Produto.
  \item[Produto:] mantém o cadastro central de produtos, base do modelo canônico, e o serviço de estoque, com o saldo único compartilhado por todos os canais (regra RN01). Fornece esses dados aos componentes Anúncio e Integração.
  \item[Anúncio:] mantém a oferta de um produto em cada canal, com seu preço, sua situação e suas métricas.
  \item[Integração:] contém a interface \texttt{ConectorMarketplace}, que define as operações comuns aos canais: publicar e atualizar anúncios, atualizar o saldo disponível, obter a quantidade disponível de cada anúncio e consultar pedidos. Cada implementação converte o modelo canônico para o formato da plataforma e trata sua autenticação e seus limites de uso. O serviço de pedidos também fica neste componente, pois os pedidos são consultados por meio dos conectores, sem serem gravados no banco, e a situação de cada um é padronizada no momento da consulta, conforme a regra RN04.
  \item[Marketplace:] representa os canais de venda, acessados apenas por meio do componente Integração.
  \item[Auditoria:] registra as operações realizadas sobre os anúncios, permitindo rastrear as alterações feitas.
\end{description}

Os conectores seguem uma meta escalonada: o Mercado Livre é a integração obrigatória; a Shopee é desejável; e a Amazon é opcional, pois depende da aprovação de uma conta de desenvolvedor. Como todos ficam atrás da mesma interface, a extensibilidade pode ser demonstrada mesmo que alguma aprovação não seja obtida a tempo. O Facebook Marketplace não terá conector, conforme a regra RN07, e a OLX não terá conector nesta etapa. Outros canais poderão ser incorporados depois, com novas implementações da mesma interface.

O serviço de estoque exige cuidados adicionais, pois uma mesma peça pode ser vendida em dois canais quase ao mesmo tempo. Para evitar a sobrevenda, cada alteração de saldo ocorrerá em uma transação com bloqueio do registro do produto. O saldo do \sistema{} é a referência para todos os canais, conforme a regra RN01. Como os pedidos são apenas consultados nos marketplaces, o sistema não mantém registro dos pedidos já processados, e a idempotência vem da comparação de quantidades: cada anúncio guarda a última quantidade enviada ao canal, e uma quantidade menor na plataforma gera uma baixa igual à diferença entre os dois valores. Uma notificação repetida encontra a diferença já aplicada e não gera nova baixa. As alterações serão percebidas por notificações (\textit{webhooks}) nos canais que as oferecerem, complementadas por uma rotina periódica (\textit{polling}) que recupera eventos perdidos e reconcilia os saldos entre o sistema e cada canal. A mesma comparação ocorre antes de cada envio de saldo, para que uma venda ainda não notificada não seja sobrescrita. Resta uma janela curta entre essa leitura e o envio, na qual uma venda pode se perder sem ser detectada; esse risco é aceito no MVP. A viabilidade dessas estratégias deverá ser confirmada para cada plataforma durante a implementação dos conectores.

\section{Modelo de Dados}

O modelo de dados do SellerHub foi concebido para suportar a centralização das operações comerciais, garantindo a integridade, a consistência e a rastreabilidade das informações compartilhadas entre diferentes canais de venda. Considerando a natureza estruturada dos dados envolvidos, como produtos, anúncios e métricas, optou-se pela adoção de um modelo relacional, implementado através do sistema gerenciador de banco de dados PostgreSQL.

A estruturação lógica traduz os conceitos do domínio em entidades e relacionamentos que viabilizam a arquitetura da aplicação:

\begin{itemize}
    \item \textbf{Pessoas e Usuários:} \texttt{CAD\_PESSOA} guarda os dados cadastrais, e \texttt{CAD\_USUARIO}, as credenciais de acesso. Uma pessoa pode ter um ou mais usuários, e cada usuário pertence a uma única pessoa. O usuário é a entidade que estabelece a responsabilidade pelos dados, pois a ele se ligam os produtos e os registros de auditoria.

    \item \textbf{Auditoria:} \texttt{CAD\_AUDITORIA} registra as operações realizadas por cada usuário, o que permite identificar o responsável por uma alteração. Cada registro pertence a um único usuário.

    \item \textbf{Produtos:} \texttt{CAD\_PRODUTO} atua como o núcleo da plataforma, armazenando atributos universais (nome, descrição base, código de identificação/SKU). Cada produto pertence a um único usuário. Como a regra RN01 define um saldo único por produto, o estoque não forma uma entidade própria e é mantido como atributo do produto, o que exige controle transacional rigoroso para que as baixas decorrentes de vendas em diferentes canais reflitam imediatamente na quantidade disponível.

    \item \textbf{Marketplaces e Anúncios:} Para suportar a funcionalidade de \textit{hub}, \texttt{CAD\_ANUNCIO} liga um produto a um marketplace específico, representado em \texttt{CAD\_MARKETPLACE}. Um produto pode ter vários anúncios, e cada anúncio pertence a um único produto e a um único marketplace. Essa entidade armazena os parâmetros inerentes àquela oferta na plataforma externa, como o preço praticado, o link de origem, a situação de publicação, a última quantidade enviada ao canal e a indicação de divergência exibida no painel.

    \item \textbf{Métricas de Desempenho:} \texttt{HIST\_METRICA\_ANUNCIO\_MP} guarda o histórico de métricas de cada anúncio. O modelo vincula quantidades de acessos e indicadores de desempenho a períodos específicos, possibilitando acompanhar a evolução de um anúncio e comparar o mesmo produto em canais distintos.
\end{itemize}

Entre as principais decisões de projeto adotadas, destaca-se a normalização dos dados para mitigar redundâncias, separando as informações estruturais do produto das informações voláteis de cada anúncio. Pedidos e vendas não formam entidades do modelo, pois permanecem nos marketplaces e são apenas consultados pelo sistema. A escolha do modelo relacional garante, através da aplicação de chaves estrangeiras (\textit{Foreign Keys}) e restrições de integridade (\textit{Constraints}), que a base de dados não admita inconsistências, como o registro de anúncios de produtos inexistentes ou o acúmulo de métricas órfãs no sistema.

\section{Projeto da Interface do Usuário}

A interface web é organizada em uma tela para cada grupo de funcionalidades. Até o momento, apenas a tela de login foi implementada; as demais estão previstas e poderão ser ajustadas com a validação junto aos lojistas. A \autoref{tab:telas} relaciona as telas aos requisitos que atendem.

A tela de produtos é o ponto de partida do fluxo principal, pois o anúncio de cada canal é preparado a partir de um produto já cadastrado, sem digitar as mesmas informações novamente. Esse aproveitamento atende à necessidade de reduzir o retrabalho de cadastro descrita na \autoref{sec:necessidades}.

As telas seguem os critérios adotados no login: validação dos campos antes do envio, mensagens de erro compreensíveis, bloqueio de envios repetidos durante uma requisição e recursos de acessibilidade, como rótulos associados aos campos. Assim, o usuário recebe o mesmo tratamento em todo o sistema, conforme o requisito de usabilidade RNF01.

\section{Comportamento do Sistema}

Esta seção descreve a colaboração entre os componentes nos principais fluxos e os estados de um anúncio. O fluxo de autenticação, já implementado, é detalhado na \autoref{sec:integracao}, e o fluxo de cadastro e publicação é representado na \autoref{fig:atividades}. Os fluxos são descritos em etapas, sem diagrama de sequência, porque ainda não foram implementados e dependem das APIs de cada plataforma.

A sincronização de estoque é o fluxo que reúne mais componentes. A cada notificação de um marketplace ou execução da rotina periódica, as seguintes etapas são previstas:

\begin{enumerate}
  \item o conector do canal obtém a quantidade disponível do anúncio;
  \item o serviço de estoque compara essa quantidade com a última enviada ao canal e com o saldo do produto; se as três forem iguais, encerra o fluxo;
  \item se a quantidade for menor que a última enviada, o serviço de estoque, em uma transação, dá baixa da diferença no saldo do produto; uma redução feita diretamente no marketplace recebe o mesmo tratamento, pois não se distingue de uma venda;
  \item se a quantidade for maior que a última enviada, o saldo não é alterado, e o painel sinaliza a divergência, pois o aumento pode indicar um cancelamento a ser marcado pelo lojista;
  \item o serviço de estoque envia o saldo aos canais por meio de seus conectores, repetindo antes a comparação com a quantidade atual de cada anúncio, atualiza a última quantidade enviada e, se o saldo chegar a zero, os anúncios do produto deixam de ficar disponíveis, conforme a regra RN02;
  \item os envios que falharem são repetidos; se a falha persistir, o painel sinaliza a divergência até que a rotina periódica conclua a atualização.
\end{enumerate}

O retorno de um pedido cancelado ao saldo é feito pelo lojista, que marca o pedido como cancelado na tela de vendas, conforme a regra RN05. A marcação soma a quantidade do pedido ao saldo do produto e dispara o envio do novo saldo aos canais, sem cancelar o pedido no marketplace. Como os pedidos não são armazenados, a marcação não fica registrada: a tela pede confirmação antes de aplicá-la, e repeti-la soma a quantidade novamente.

Um anúncio passa pelas situações definidas na regra RN06, representadas na \autoref{fig:estados}. Todo anúncio começa como rascunho e permanece nessa situação enquanto os campos exigidos pelo marketplace não forem atendidos. Um anúncio publicado pode ser pausado pelo vendedor ou automaticamente, quando o saldo do produto chegar a zero, e só retorna à publicação com saldo positivo.

\section{Segurança e Controle de Acesso}

As decisões de segurança atendem aos requisitos RF01, RNF02 e RNF08. As medidas já implementadas no fluxo de autenticação são detalhadas no \autoref{cap:implementacao}: armazenamento apenas do hash bcrypt das senhas, resposta idêntica para e-mail inexistente e senha incorreta, limite de tamanho do corpo das requisições, mensagens de erro sem detalhes técnicos, autorização de uma única origem pelo mecanismo CORS e manutenção das credenciais fora do repositório, no arquivo \texttt{.env}.

Ainda falta o gerenciamento de sessão. Hoje, a API apenas confirma se as credenciais são válidas e, por isso, as demais rotas não podem ser protegidas. Antes da criação dos módulos de negócio, será necessário definir o mecanismo de sessão e exigir que toda rota, exceto a de login, verifique se o usuário está autenticado.

Quanto ao controle de acesso, a regra RN08 restringe o MVP a uma única conta, compartilhada pelos administradores da loja. Por esse motivo, o sistema não tem perfis nem permissões distintas, e todas as funcionalidades exigem apenas autenticação.

As credenciais de acesso às APIs dos marketplaces ficarão somente na API do \sistema{}, nunca na interface web nem no repositório, e cada conector solicitará apenas as permissões necessárias às suas operações. As notificações recebidas por \textit{webhook} deverão ter sua origem verificada com os mecanismos oferecidos por cada plataforma, para que uma requisição forjada não dispare consultas e atualizações indevidas.

A consulta de pedidos pode trazer dados pessoais de compradores, como nome e endereço. Em atenção à LGPD (RNF08), esses dados serão apenas exibidos ao vendedor e não serão gravados no banco. Quando o sistema for executado fora da máquina local, a comunicação entre o navegador e a API deverá ocorrer por HTTPS, pois as credenciais trafegam nas requisições de login.
